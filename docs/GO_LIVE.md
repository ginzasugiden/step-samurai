# step-samurai 本番GOランブック

本番の実送信を開始する際、**上から順番に**実行する。各ステップの確認が取れてから次に進むこと。
このドキュメント自体はコード変更を伴わない運用手順書であり、実行は全てユーザー自身がGASエディタ等で行う。

前提: [[GO_LIVE_DATEの実値についての注意]]（下記(3)参照）。本ランブック作成時点の監査で、GO_LIVE_DATEの実値が想定（2026-06-30）と異なる可能性が判明している。(3)で必ず実値を確認すること。

## (1) トークンローテーション

GASエディタで `rotateTokenTokyoflower` を実行する。

- 実行ログに新しい平文トークンが出力される（この時点でしか表示されない。控えること）
- 実行と同時に旧トークンは失効するため、`webui`側のログイン画面で新トークンを使って再ログインし、「設定」タブが正常に表示されることを確認する
- 旧トークンでログインしたままの画面があれば、その画面は以後APIが401/unauthorizedを返すようになる

## (2) EXCLUDE_ORDERS の設定（必要な場合のみ）

`本番送信手前の監査`で ship_date の不整合や原因不明の挙動が疑われた注文番号がある場合、原因が判明するまでの一時措置として Script Properties に `EXCLUDE_ORDERS`（カンマ区切りの order_number）を設定する。

- 対象が無ければ設定不要（未設定=除外なしがデフォルト）
- 設定した場合、`sendPendingMails`実行時にログへ `EXCLUDE_ORDERS設定によりスキップ（一時措置）` と出力される
- 原因判明後は値を空にして通常運用へ戻すこと（恒久設定にしない）

## (3) GO_LIVE_DATE の最終確認

GASエディタの「プロジェクトの設定」→「スクリプト プロパティ」で `GO_LIVE_DATE` の**実際の値**を確認する。

**重要**: 本ランブック作成のきっかけとなった監査で、この値は「2026-06-30」という前提で会話を進めてきたが、実データの整合性から**実際には2026-07-01等、別の値である可能性**が指摘されている（詳細は監査報告を参照）。本番送信前に必ず実値をここで確認し、意図した日付になっているか判断すること。過去に遡って送るほど対象件数が増える点に注意。

## (4) DRY_RUN を false にする

Script Properties の `DRY_RUN` を `true` → `false` に変更する。**これが実送信の最終スイッチ。** 変更前に(1)〜(3)が完了していることを再確認すること。

## (5) 初回送信の実行と目視確認

GASエディタで `runFollowMailsOnly` を手動実行する。

- 実行ログで送信件数・エラーの有無を確認する
- テナントスプレッドシートの `sends` タブに新しい行（result='sent'）が追加されていることを確認する
- ロリポップ側の bridge.log（`smtp_bridge.php` の送信ログ）で、実際に外部SMTP経由の送信が成功しているか確認する
- 件数が想定より大きく異なる場合は、直ちに(7)のロールバックを検討する

## (6) 毎時トリガーの登録

問題がなければ、GASエディタの「トリガー」画面（時計アイコン）から `runHourlyFollowPipeline` を毎時実行のトリガーとして手動登録する。

- **`runPipeline`ではなく`runHourlyFollowPipeline`を登録すること**（クーポン経路は(8)の保留事項が解決するまで動かさない設計のため）
- 登録はこのタイミングまで意図的に行っていない（それまでは手動実行のみで様子を見る）

## (7) ロールバック手順

異常が見つかった場合、直ちに以下を実施する。

1. Script Properties の `DRY_RUN` を `true` に戻す
2. GASエディタの「トリガー」画面から `runHourlyFollowPipeline` のトリガーを削除する
3. 必要であれば `EXCLUDE_ORDERS` に問題のあった order_number を追加する
4. 原因調査後、本ランブックを(1)からやり直す

## (8) 保留事項（本番GO時点での既知の未解決課題）

- **クーポンAPI**: 楽天Coupon API（`/es/1.0/coupon/issue`, XML形式）の仕様が未解決のため、`runHourlyFollowPipeline`はクーポン経路（evaluateCoupons/issueCoupon）を呼ばない設計にしている。クーポン配信を有効化するには別途このAPI仕様の確認・検証が必要
- **review_fetcher.py の常時稼働**: レビュー取得はSelenium版`review_fetcher.py`（本リポジトリ外）が担っているが、新しいPCでのタスクスケジューラ登録がまだ済んでいない。これが動いていないと`reviews`タブが更新されず、クーポン判定（レビュー必須条件）が機能しない
- **ship_date空欄の注文の扱い**: 監査時点で「shipped」ステータスなのに`ship_date`が空の注文が多数存在することを確認済み（件数・一覧は監査報告参照）。これらはフォローメール対象の判定から現状単純に除外されているが、根本原因（RMS API応答に出荷日が含まれないケースがある等）の調査と対応方針は未定
