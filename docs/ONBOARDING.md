# ステップ侍 他店舗導入ガイド（運営者向け）

外部の楽天店舗にステップ侍（受注取得・フォローメール・店舗分析）を提供するときに、
**店舗から受け取る情報**と**運営側の作業**をまとめる。店舗のログイン情報（R-Login / 楽天会員ID・パスワード）は預からない。

## 1. 店舗に提供してもらう情報（依頼シート）

| # | 項目 | 取得場所（店舗側の操作） | 用途 | 必須 |
|---|---|---|---|---|
| 1 | 店舗名・店舗ID（sid = 店舗URL末尾） | RMS トップ右上 | 表示・問い合わせURL生成 | ◎ |
| 2 | **serviceSecret / licenseKey** と **licenseKey の有効期限** | RMS →「店舗設定」→「WEB API」→ 楽天ペイ受注API の利用申請 → ライセンスキー発行（**ライセンスキーは1年で失効**） | 受注取得（searchOrder / getOrder）。今後クーポン発行にも使用 | ◎ |
| 3 | **店舗連絡先メールアドレス**（RMSの「店舗連絡先」に登録済みのもの） | RMS →「店舗設定」→「基本情報」 | フォローメールの差出人。楽天あんしんメルアドは**この差出人でないと届かない** | ◎ |
| 4 | **あんしんメルアドサービス SMTP ID / パスワード** | RMS →「メール」→「あんしんメルアド SMTP設定」で発行 | 店舗名義でマスクアドレス宛に送るために SMTPブリッジへ登録 | ◎ |
| 5 | 控えメールアドレス（cc） | 任意 | 送信メールの控え | 任意 |
| 6 | 稼働開始日（go_live_date） | 店舗と合意 | この日以降に発送した注文だけがフォロー対象。過去客に一斉送信しないためのガード | ◎ |
| 7 | 発送後何日でフォローするか（既定5日） | 店舗と合意 | settings.follow_days_after_ship | ◎ |
| 8 | フォローメール文面の希望（既定文面を提示して赤入れ） | 店舗 | templates.follow_v1。店舗自身が管理画面から編集可 | 任意 |
| 9 | レビューCSV（RMS レビューチェックツールからダウンロード） | 店舗が週1回など | レビュー率・評価分布。管理画面「レビュー取込」タブから店舗自身が取り込む | 任意 |

**受け取り方**: 2・4 は秘密情報。メール本文に書かせず、パスワード付きファイルや1回限りの共有リンクで受け取り、api_key シート / config.php に登録後は原本を削除する。

**店舗に事前に伝えること**
- 楽天のガイドラインどおり、レビューを条件にしたクーポンは「投稿者全員に一律」でのみ運用する（評価の高低で差をつけない）
- フォローメールは店舗名義・店舗の差出人で送られる。配信停止の申し出は店舗側で `settings.exclude_orders` に注文番号を入れる（または運営に連絡）
- 受注データは店舗専用のスプレッドシート1ファイルに保存され、他店舗からは構造上アクセスできない（docs/MULTITENANT_SECURITY.md）

## 2. 運営側の作業手順（webui/admin.html）

管理者画面（ADMIN_TOKEN でログイン）で以下を順に実行する。GASエディタを開く必要があるのは太字の項目だけ。

1. 「新規テナント作成」: tenant_id（英小文字）/ 店舗名 / 店舗メール → 専用スプレッドシートと settings/templates が作られ、状態 `setup`・`dry_run=true` で登録される
2. **api_key シート**（`1iYeV2SbOVoRH8Qjm2d1w5tWmhlE_zcc-yO1tDSLN7Rk`）に行を追加: `id`=tenant_id, `sid`, `sname`, `serviceSecret`, `licenseKey`（値は `BASE64:` 接頭辞＋Base64）, `expiry`
3. 「操作」→ RMS 接続チェック → `http_code: 200` を確認
4. **SMTPブリッジ**: 「操作」→ config.php 追記内容を表示 → `X:\projects\step-samurai-bridge\config.php` に追記 → WinSCP でアップロード。店舗メール宛にテスト送信して到達を確認
5. 「設定」→ `go_live_date` を設定（未来日でよい）。`follow_days_after_ship` を店舗の希望値に
6. 「操作」→ 遡及取得を開始（13ヶ月・約30分・自動継続）。完了後「データ確認」で `p2_orders_rows` と `p3` を確認
7. 「操作」→ 店舗トークンを発行 → 店舗へ渡す。店舗は `webui/index.html`（設定・文面・テスト送信・レビュー取込）と `webui/analytics.html`（店舗分析）にこのトークンでログインする
8. 店舗が index.html「テスト送信」で文面を確認（宛先は店舗メール固定、dry_run=true の間は送られずログのみ → 確認時は一時的に dry_run=false にして1通送り、戻す）
9. 稼働: 「設定」→ `dry_run=false`、「操作」→ 状態を `active`。前提（認証情報・go_live_date・follow_days・follow_v1）が揃っていないと active にできない

## 3. レビューについて（外部店舗の方針）

楽天のレビューAPIは利用できず、tokyoflower では Selenium で RMS にログインして取得している。外部店舗の R-Login や楽天会員ID・パスワード・SMS認証を預かることは、店舗のリスク・楽天規約・SMS OTP による自動化断念の3点から採用しない。

外部店舗は **CSV取込方式**（管理画面「レビュー取込」タブ）で運用する。店舗が RMS「レビューチェックツール」からCSVをダウンロードして選ぶだけで、列は自動判定・重複取込なし・注文との紐づけも自動。週1回の運用で、レビュー率・星分布・レビュー投稿リードタイムが揃う。

将来、店舗が RMS のサブユーザー（閲覧権限のみ・SMS不要の運用）を発行できる場合は、tokyoflower と同じ自動取得に切り替えられる。

## 4. 解約・停止

- 一時停止: 状態を `paused`（パイプライン対象外・店舗はログイン可）
- 解約: 状態を `disabled`（シートへのアクセス拒否）→ トークン全失効 → api_key 行と config.php の設定を削除 → 店舗専用スプレッドシートを店舗へ譲渡または削除
