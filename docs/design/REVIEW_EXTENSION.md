# レビュー取得 Chrome 拡張 設計書（案）

作成日: 2026-10-24 / 状態: 設計のみ（未実装・未承認）
注意: 本書には購入者情報・レビュー本文・URL/注文番号の実値を含めない。列名・要素名のみを記す。

## 1. 結論（実現性）

**判定: 条件付きで実現できる。**

- 技術的には実証済み。ECOS の Chrome 拡張（ECDashboard `extension/`）が、ログイン済みの RMS タブから「レビューチェックツール」CSV を `GET` で取得し、tokyoflower で本番稼働している（初回 7,714 件を取得済み）。CSV 取得に CSRF トークンは不要で、一覧 HTML のパースにも依存しない。
- 「ログイン情報を預からない」は維持できる。拡張は RMS のセッション Cookie を使うだけで、ID・パスワードを読み取り・保存・送信しない。
- 条件（外部店舗へ配る場合に未整備）:
  1. 送信先が ECOS 固定。外部店舗向けには GAS へ直接送る経路と、店舗ごとの認証が必要。
  2. 認証方式の決定（§2.4）。
  3. `import_reviews` の既存行上書き問題（§5）の修正。
  4. 規約・プライバシーポリシーの改定（§6）と Chrome ウェブストア限定公開の準備（§4）。
  5. RMS 側の画面・CSV 仕様変更時に止まる前提の運用（§3）。

## 2. 拡張機能の構成

### 2.1 方針
- ECOS 拡張とは別の **店舗配布用の専用拡張**（Manifest V3）を新規に作る。ECOS 拡張は権限が広く（RMS 全体・任意ホスト・webRequest 等）、店舗に配るには過大なため流用しない。CSV 取得・Shift_JIS デコード・ヘッダ検出・ページ分割のロジックは ECOS 拡張の `review-csv.ts` / `csv.ts` / `content.ts` を参考に移植する。

### 2.2 権限（最小）
| 区分 | 値 | 用途 |
|---|---|---|
| host_permissions | `https://review.rms.rakuten.co.jp/*` | CSV 取得（`/search/csv/`） |
| host_permissions | `https://script.google.com/macros/s/*`、`https://script.googleusercontent.com/*` | GAS への送信（POST は 302 で後者へ飛ぶ） |
| permissions | `storage`, `alarms` | 設定・進捗の保存、リマインド |
| permissions | `scripting` | 要検証（content_scripts 宣言で足りるなら外す） |
| 持たないもの | `tabs`, `webRequest`, `notifications`, `cookies`, 任意ホスト | 最小化のため |

- `content_scripts` は `https://review.rms.rakuten.co.jp/*` のみ。ECOS の `*.rms.rakuten.co.jp` 全体は不要。
- 要検証: 通知（`notifications`）を使わずバッジ表示のみで足りるか。

### 2.3 動作のきっかけ
1. **手動**: ポップアップの「今すぐ同期」ボタン。
2. **RMS レビュー画面を開いたとき**: content script が起動し、前回同期から 20 時間以上経っていれば自動で 1 回同期（1 日 1 回上限）。
3. **リマインド**: `alarms` で 1 日 1 回、前回同期が 3 日以上前ならバッジに「!」を出す（RMS を開く動機づけ。バックグラウンドで勝手に RMS を開かない）。

- 取得処理は RMS タブ内（同一オリジン、`credentials:'include'`）の `fetch`。
- 取得範囲: 初回は全期間（年単位に分割。3,000 行に達したら二分割。実測では 3,000 行で打ち切られる）、以降は直近 14 日。進捗は `storage` に保持。
- 削除判定を ECOS のように拡張側で持つかは §9 で決める（tokyoflower の仕様では「観測できなくなったら deleted」）。

### 2.4 送信データ
最小項目（必須）: `review_id`（レビュー詳細URL）、`order_number`、`rating`、`posted_at`。
任意（要判断・§9）: `review_type`、`title`、`body`、`product_title`。

- 500 件ずつ分割して POST（GAS 側上限に合わせる）。`Content-Type: text/plain`（GAS は CORS プリフライトに応答できないため。拡張の background からの送信なら問題なし）。
- 購入者名・メール・住所等は CSV に含まれないため送らない。
- 注文番号の桁数は一定でない（末尾の数字が 8〜10 桁）。形式の厳密検証は「数字-数字-数字」程度に留める。
- 投稿日は `YYYY/MM/DD H:MM:SS` 形式（時が 1 桁になりうる）。GAS 側で正規化済み。

### 2.5 店舗トークンの保存と失効
- **専用の「拡張連携トークン」**を新設する（案B）。管理画面のセッショントークン（12 時間で失効）や、全アクション可能な `kind=token` は使わない。
  - スコープはレビュー取込のみ。tenant_id はトークンから `verifyTenantToken_` 系で解決し、リクエスト本文の tenant_id は信用しない（既存の安全設計に沿う）。
  - 管理画面で発行・再発行・無効化できる。無効化すれば拡張は次回送信で `unauthorized` となり停止する。
  - シートには平文を残さずハッシュで保持する方向（既存方式との整合は実装時に確認）。
- 拡張側は `chrome.storage.local` に保存（`sync` は使わない）。Cookie・パスワードは保存しない。
- 比較案A（既存 `ingest_reviews` + `REVIEW_INGEST_KEY__<tenant>`）は、Script Properties への登録が運営の手作業のみ（clasp run も Chrome も不可）で、店舗が自力で設定できないため外部展開に向かない。tokyoflower 用の現行経路は変更しない。
- 受信ガード: `settings.review_ingest_enabled` を新アクションにも適用（fail-closed）。

## 3. エラー時の挙動と運営への通知

| 事象 | 検知 | 拡張の挙動 | 運営への通知 |
|---|---|---|---|
| RMS 未ログイン | 最終 URL がログインページ判定、または応答に password 入力 | 何も送らず中断。バッジ「ログイン要」＋ポップアップに案内 | 直接は通知しない。無同期が続けば下記の失効検知 |
| 画面/CSV 構造の変更 | ヘッダ検出失敗、列数不一致、`/search/csv/` が非 CSV を返す | **送信せず停止**（部分的に壊れたデータを送らない）。バッジ「要更新」 | 同上＋拡張からの「状態通知」（件数・値を含まない最小 ping）を検討 |
| トークン失効/不正 | GAS が `unauthorized` | 再試行しない。停止し、再設定を案内 | 管理画面側の最終受信日時で把握 |
| 受信無効 | `review_ingest_enabled` が false | 再試行しない。案内表示 | 同上 |
| ネットワーク/GAS 一時障害 | 5xx・タイムアウト | 最大 3 回再試行（1s/3s/9s）、以降は次回に持ち越し | なし |
| 3,000 行上限到達 | 行数が上限と一致 | 期間を二分割して再取得 | 分割しても到達した場合のみ警告 |

- **運営への通知は GAS 側の日次チェックで行う**（拡張が止まると拡張自身は何も送れないため）。受信ごとに `settings` へ最終受信日時を記録し、既存の日次トリガー（`checkPurgeReminders_` と同様の仕組み）で「有効テナントなのに 3 日以上受信なし」を運営宛メールで通知する。メールには tenant_id と日数のみを書く。
- 拡張からの最小の状態通知（`ext_status`: 版数、エラー種別コードのみ）を追加するかは §9。

## 4. Chrome ウェブストア（限定公開）の準備

- 公開設定: 「限定公開（Unlisted）」。リンクを知る店舗のみがインストール可。デベロッパー登録（登録料）とアカウントの 2 段階認証が必要。
- 提出物:
  - 拡張の単一目的の説明: 「楽天 RMS のレビューを、店舗自身の step-samurai に取り込む」。
  - **権限ごとの正当化文**（案）
    - `review.rms.rakuten.co.jp`: ログイン済みのレビューチェックツールからレビュー一覧 CSV を取得するため。
    - `script.google.com` / `script.googleusercontent.com`: 取得したレビュー項目を、店舗自身の step-samurai（Google Apps Script）に送信するため。
    - `storage`: 連携トークンと前回同期日時を保存するため。
    - `alarms`: 前回同期から日数が経過した際にバッジで知らせるため。
  - リモートコード実行なし（宣言）。
  - データ使用の開示: 取得するのは「レビューの評価・投稿日・注文番号・（任意）本文」。ID・パスワード・Cookie は取得しない。第三者への販売・目的外利用なし。
  - **プライバシーポリシーの URL**: `privacy.html` に拡張の節を追加して指定（§6）。ストアのポリシーでは取得データの種類・用途・送信先・保管の記載が必要。
- 審査対策: 権限は最小、説明と挙動を一致させる。ストアのスクリーンショット（ポップアップ、連携設定、権限説明）と、操作説明の動画または手順ページを用意する。
- 配布の運用: 更新は審査を経るため RMS 仕様変更への即応が難しい。設定値（URL テンプレート等）をコードに埋めず、少数の設定で吸収できる作りにする（ただしリモートコード禁止のため、設定はデータのみ）。

## 5. GAS 側の変更

1. 新アクション（案: `ingest_reviews_ext`）: 拡張連携トークンで tenant を解決し、既存の取込ロジック（`reviews_ingest.gs`）を再利用。500 件上限・`review_ingest_enabled` ガード・列追加は末尾のみ（既存パターン踏襲）。
2. 拡張連携トークンの発行・再発行・無効化（管理画面と GAS）。
3. `reviews_import.gs` の更新時に、ingest 由来の追加列（`review_type`〜`matched`）を空で上書きする問題を修正（既存行ベースで更新）。併用する店舗で必須。
4. 3 項目（注文番号・評価・投稿日）だけでも取り込めるが、レビューID を合成するため、同一注文・同一時刻の別レビューが衝突する。**詳細URLを加えた 4 項目を最低線**とする。
5. `linkOrdersReviews` は削除フラグ付きレビューも `review_linked=true` にする。拡張で削除判定を扱うなら整合を取る。
6. 最終受信日時の記録と、日次の「受信途絶」通知。

## 6. 規約・プライバシーポリシー 改定案（規約 v1.1）

現行の構成は全12条（第2条サービス内容、第5条店舗の責任、第8条解約とデータの扱い 等）。取得項目の網羅列挙は privacy.html に委ねている。

| 箇所 | 変更案 |
|---|---|
| 第2条（サービス内容）のレビュー関連 | 「店舗がアップロードした CSV」に加え、「店舗が導入する専用の Chrome 拡張機能により、店舗自身がログインした RMS 画面から取得したレビュー情報」を対象に追記。取得主体は店舗であること、運営は店舗の RMS ログイン情報（R-Login・楽天会員ID・パスワード・SMS認証）を預からないことを明記 |
| 第5条（店舗の責任） | 拡張のインストール先ブラウザ・連携トークンの管理責任、トークン漏えい時の再発行、楽天の利用規約を遵守して取得することを追記 |
| 新設（案: 第5条の2「拡張機能」） | 取得するレビュー項目、送信先（店舗専用スプレッドシート）、取得は店舗の操作・設定に基づくこと、RMS 仕様変更で動作しない場合があること（免責は第6条と整合） |
| 第6条（免責） | RMS の仕様変更・ストア審査・ブラウザ更新による取得停止は保証しない旨 |
| 第8条（解約とデータの扱い） | 解約時に連携トークンを無効化・削除。削除対象にレビュー情報を含める（現行「30日以内に削除」と `purge.gs` の挙動の整合も確認） |
| privacy.html（取得する情報・委託の節） | レビュー項目に拡張経由の取得を追記（評価・投稿日・注文番号・レビュー詳細URL・（任意）タイトル/本文/商品名）。拡張が取得しないもの（ID・パスワード・Cookie）を明記。委託先は Google（GAS）。ECOS を経由させる構成にする場合は委託先・経由先に追記が必要 |
| 受注データの項目・用途の一覧 | 受注タブ18列の項目と用途を明記（§7） |

## 7. 受注タブの全列と用途（規約への明記案 = 案A）

初期 13 列 + 分析用 5 列 = 18 列。保存しないもの: 番地を含む住所、電話番号、郵便番号。

| 列 | 区分 | 主な用途 |
|---|---|---|
| order_number | 識別子 | 注文の一意キー、レビュー・送信履歴との突合 |
| order_date / order_datetime | 非個人 | 集計期間、購入回数計算、時間帯別集計 |
| buyer_key | 個人情報（購入者識別） | 同一購入者の判定、購入回数、送信履歴、クーポン判定 |
| masked_email | 個人情報（メール） | メールの宛先、新規/リピート判定 |
| buyer_name | 個人情報（氏名） | メール本文の宛名 |
| item_code / item_name | 非個人 | 商品別集計 |
| amount / goods_price | 非個人 | 売上集計、月次レポート |
| units | 非個人 | 点数集計 |
| purchase_count | 派生 | リピート判定、クーポン条件 |
| prefecture | 個人情報の一部 | 都道府県別集計 |
| ship_date | 非個人 | フォロー・お礼メールの送信時期判定 |
| status | 非個人 | 送信対象の判定（キャンセル除外）、集計母集団 |
| review_linked | 非個人 | レビュー率、クーポン条件 |
| coupon_shop_price / coupon_codes | 非個人 | クーポン利用の集計 |

- `sends` タブに `buyer_key`（メールアドレスが入りうる）があるため、規約・プライバシーの列挙時に sends も確認する。
- 「購入者ニックネーム」は CSV アップロード時のみ。拡張経由の CSV に含まれるかは未確認（実測の CSV 列には無い）。

## 9. 未確認事項（ライブ画面での確認）
1. レビュー一覧画面の描画方式（初期 HTML か JS 後読込か）。CSV 方式なら不要だが、画面導線を使う案なら必要。
2. 画面の「CSVダウンロード」の実体（`/search/csv/` への GET リンクか）。拡張は GET で実績あり。
3. 3,000 行で打ち切りがあるか、画面に警告が出るか。
4. CSV の「フラグ」「未対応フラグ」列の意味（フラグは 1 件のみ 1）。
5. 注文番号末尾の桁数がばらつく理由。
6. RMS のいずれかのタブを開いていないと CSV が取れないか（同一オリジン fetch のため）。
7. 旧 Selenium 版 review_fetcher.py が現在も稼働しているか（稼働していれば ID・パスワードを保持した状態で、外部説明との整合に影響）。
8. tokyoflower 本番で拡張経路が稼働しているか（GAS エディタの `previewReviewIngestStatusTokyoflower()`、読み取りのみ）。
9. `purge.gs` が orders を実際に削除するか（現状はシート名変更での退避に見える。規約第8条「30日以内に削除」との整合）。
